# 第⑧步：效度校验

## 目标

在进入分析之前，确认**这次运行的数字可信**。

**不通过时要指出退回哪一步**，而不是笼统地说"评测失败"。校验只做判断，不修改任何产物——要改就回退到相应步骤重做。

## 前置

- 运行目录中已有 `metrics.json`

## 本步不做的事

- **不解释原因**（第⑨步）。校验只回答"这批数字可不可信"，不回答"为什么差"
- **不修改任何产物**。要改就回退重做
- 不重新判定、不重新检索——除非校验结论是"判定标准有问题"

## 先分清：回退信号与校验项

用户说"**你这个方向完全搞错了**"不是校验不通过，**是回退信号**。校验针对本次运行的输出；方向性问题意味着此前某个确认环节出了偏差。

| 用户说 | 真正错的是 | 退回 |
|---|---|---|
| "这些方向不是用户会问的" | 方向或比重 | 第③步 |
| "我们线上不这么问" | 形态判断 | 第③步 |
| "你测的不是我想测的东西" | 链路选择或接入层 | 第②步 |
| "这个判定标准不对" | 判定口径 | 第④步提版本 → 重走 ⑤⑥⑦ |
| "评测集里这些题不该有" | 出题 | 第⑤步或第⑥步 |

**回退后要重走受影响的下游**，见 SKILL.md 的「随时可以回退」。

## 校验一：自动断言

**成本最低，先跑。适合写成脚本。**

- **范围**：各指标是否都落在合法区间内
- **关系**：指标之间的上下界与单调关系。**按规格里实际用到的指标去推导**，不要照抄一组固定的——k 被限死时很多常见关系不适用
- **判定覆盖率**：每条可回答的条目是否都有判定。**漏判会让指标虚高**，而且不报错
- **空结果率**：有多少条查询返回空。这是一个事实，不是错误，但必须报出来——它往往比任何指标都更能说明问题
- **全判无关的条目**：如果一批条目所有返回值都被判无关，先怀疑**判定过严**或**要点标错**，而不是系统
- **样本量与规格的偏差**：各分层实际条数与 `spec.size` 是否一致

## 校验二：目视复核

抽一定比例的判定明细交给用户看。**用户判断的是"这条结果被判为部分相关是否合理"，不是"总分对不对"。**

抽样要分层，并**刻意包含最易暴露判定缺陷的类型**：

- 超出知识范围的查询（拒答判对了没有）
- 答案分散在多处内容块的查询
- 检索结果中含高度重叠内容的查询

**同时把要点与源块一起给它**——要点可能经过整理，单看要点判不准。

## 校验三：模式识别

有些现象本身就是信号：

| 现象 | 更可能的原因 |
|---|---|
| 全部方向一致偏低 | **判定过严**或 rubric 不合适，而不是系统差 |
| 个别方向偏低 | 该方向的题目难度或术语生僻，不是检索层的问题 |
| 全部条目都接近满分 | **判定过松，或者题目泄漏**（见下节） |
| 某条链路与其它链路的指标差一个量级 | 先怀疑该链路的配置，而不是系统 |
| 大量条目返回空 | 阈值、链路选择，或库本身的问题 |

**这些只是"更可能"，不要当结论。** 记下来交给第⑨步。

## 必做：评测集泄漏检查

**查询如果大量沿用源块的原文措辞，检索难度会被人为降低，指标虚高。**

第⑤步打样时和第⑥步生成后都算过一遍，这里是**终检**：

- 算每条查询与它源块的 n-gram 重合度，报告分布
- 与前两次的分布对比，明显变差说明有环节跑偏
- **按形态分开看**：关键词形态天然会用库里的术语，重合度本来就高；**自然语言形态重合度高才是问题**

占比异常时，修法是**回第④步在规格里加约束**（例如"生成时不得照抄源块措辞"），然后重走第⑤⑥步。

## 必做：要点可靠性

消费第⑥步留下的**要点与源块一致性筛查名单**——那些最长公共子串比例偏低的要点。

当时只做了筛查没下结论，现在逐条判断：

| 情况 | 结论 |
|---|---|
| 源块本身可读性不高（图片、表格或特殊格式没被正常解析），要点由它整理而来 | 正常。属于**库的问题**，留给第⑨步归因 |
| 源块可读性正常，要点却对不上 | **要点有问题**，回第⑥步重出这几条 |

## 输出格式

写入运行目录的 `validation.json`：

```json
{
  "version": 1,
  "step": 8,
  "validated_at": "<ISO 8601 时间>",
  "spec_version": "1.0",
  "assertions": [
    { "name": "<检查项>", "status": "pass", "detail": "<说明>" }
  ],
  "leakage": {
    "by_style": {},
    "compared_with": ["step-05", "step-06"],
    "verdict": "<正常 / 需要处理>"
  },
  "point_reliability": {
    "checked": 0,
    "suspect": 0,
    "needs_regeneration": 0
  },
  "human_review": { "sampled": 0, "disagreements": 0 },
  "patterns": [],
  "verdict": "pass",
  "rollback_to": null
}
```

字段说明：

| 字段 | 说明 |
|---|---|
| `assertions` | 每项检查的名称、状态（`pass` / `warn` / `fail`）与说明。**失败的写清是什么、影响什么** |
| `leakage.by_style` | **按形态分开报**，不要只给一个总数 |
| `point_reliability` | 消费第⑥步筛查名单的结果 |
| `human_review` | 目视复核抽了多少条、其中用户不认同几条 |
| `patterns` | 观察到的模式，**只描述现象，不作因果解释** |
| `verdict` | `pass` / `pass_with_caveats` / `fail` |
| `rollback_to` | 不通过时填退回第几步；通过则 `null` |

**顶层字段集合固定，不要新增。**

## 完成后

向用户报告以下四项，然后停下：

1. 各项断言的结果，**失败项要说明影响**
2. 泄漏检查结果（按形态分开）
3. 要点可靠性：核了多少、几条有问题
4. 校验结论：通过、带保留通过、还是不通过——**不通过就指明退回第几步**

结尾按 SKILL.md 的「每步的收尾」写。例如：

> 效度校验完成，各项断言都通过了（有几条只作参考的分层已在报告里标注）。这批数字可以作为下一步分析的依据。下一步是归因分析——定位问题出在哪一层、给出改进方向。需要推进吗？
