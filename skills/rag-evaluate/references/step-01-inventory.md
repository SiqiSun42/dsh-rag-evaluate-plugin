# 第①步：清点

## 目标

在**被测工作区**中清点三件事，并把它们整理为候选链路：

1. 有哪些向量库
2. 有哪些查询入口
3. 入口与向量库集合之间的绑定关系

**本步只做存在性清点。** 不判断能不能跑、返回值是什么形态、效果如何——那些属于第②步。本步不导入、不调用被测代码，也不加载模型。

**本步的价值**在于：在投入评测之前，快速暴露"部件不全"这类结构性问题——例如只有向量库没有查询入口、入口引用的集合并不存在、或者系统形态与预期不符。这类问题一旦漏过，后面每一步都会建立在错误的前提上。

## 核心概念：链路

**评测的单位是链路，不是文件。**

一条链路 = 查询入口 × 参数组合 × 向量库集合。

- 一个向量库目录里可能包含多个集合，构成逻辑上的多个库
- 一个查询入口可能存在多种参数组合，构成完全不同的检索链路
- 入口与集合之间通常存在绑定关系（入口内部把参数映射到集合）

因此不要问"工作区里有哪些向量库文件"，要问"工作区里有哪些可评测的链路"。

## 执行步骤

**1. 确定被测工作区与本次运行**

- 按 SKILL.md 的「被测工作区与输出目录」「开始之前」两节确定本次运行的目录
- 检查该目录是否位于版本控制仓库内且未被忽略，是则提示用户
- 只在这个目录内写入，不改动工作区里的任何已有文件

**2. 清点向量库**

- 按目录结构特征识别已知类型的向量库。不同向量库有不同的文件布局特征，例如固定的元数据文件、索引文件、集合目录等
- 对每个候选记录：类型、路径、以及其中包含的集合列表
- 集合列表可读自库自身的目录文件，这属于清点而非打开
- 仅按文件结构判定，未用对应程序库打开的，如实标记

**3. 清点查询入口**

- 在代码中搜索访问向量库的位置：检索、查询、相似度搜索、嵌入编码等调用点
- 对每个候选记录：所在文件、符号名、行号

**4. 确认绑定关系**

- 入口内部通常存在参数到集合的映射：配置表、语言分支、环境变量、硬编码常量等
- 把每个入口与它引用的集合对应起来
- 若入口引用的集合在向量库中不存在，记为存在性缺口，不要跳过

**5. 枚举可达链路**

- 列出入口的公开参数及其默认值
- 找出工作区内对该入口的实际调用点，记录实际传入的参数
- **两者不一致时必须分别记录**——它们对应不同的链路。这类差异经常出现在"签名默认关闭、实际调用开启"的可选功能上
- 每条链路标注来源：
  - `observed`：在工作区的调用点中找到
  - `reachable`：仅通过公开签名可达，工作区内没有调用点

**6. 产出画像文件**

- 写入 `<运行目录>/rag-profile.json`，格式见下方

**7. 向用户报告**

- 候选链路清单
- 存在性缺口
- 需要用户确认的问题

## 判断规则

**只在以下两类情况下停下来问用户**，其余一律自己决定并在结果里报告：

- **确实找不到查询入口**——说明缺少什么能力。请 Agent 结合当前可用的其他工具给出具体建议；本 skill 只能描述缺少的能力，无法知道环境里有哪些其他插件
- **发现结果明显不完整**——例如只找到向量库但代码中完全没有访问痕迹

**以下情况不要停下来问：**

- **链路选择**：本步不做取舍，**全部记入画像**。本步不执行任何东西，成本为零；选哪几条留到第②步开始时由用户决定——从第②步起才开始真正执行
- **输出目录**：使用默认值，只在异常时（不可写、疑似会污染版本控制、目录归属不明）报备
- **推断得出的判断**：给出结论 + 标注依据，允许事后纠正，不要因此打断流程

## 注意事项

- **本步不执行被测代码。** 不导入它、不调用它、不加载模型。执行属于第②步往后。
- **本步的证据只能来自被测工作区。** 工作区里的代码引用了不存在的路径，如实记为"引用的路径不存在"即可，不要到工作区之外去找替代品。
- **不要给出属于第②步的结论**，例如向量维度、规模、返回值形态。即使能从文件反推出来，也留到第②步实测时一并确认——那时才有依据。
- **"能按文件结构识别"不等于"能打开"。** 本步只做前者，标为未打开验证，不要冒充已确认。
- **区分实测与推断。** 凡是推断得出的字段都要标注来源，不要与实测值并列呈现。
- 本步的产物是"候选 + 待确认问题"，而不是一段对话。

## 什么算缺口

`gaps` 只放**阻碍评测当前系统**的缺失。写进去之前先问一句：

> **没有它，能不能对"当前的系统"跑出指标？**

- 能跑出指标 → **不是缺口**
- 只影响"改完之后再测"的能力 → **不是缺口**，那属于第⑧步的建议范畴

**典型的不是缺口**（都属于改进能力，不属于测量能力）：

- 索引无法重建、源语料缺失
- 构建脚本硬编码、没有参数化的写入路径
- 阈值失效、召回偏低、结果不相关

**典型的缺口**：

- 入口引用的集合在向量库中不存在 → 一调用就失败，指标无从谈起
- 存在向量库但没有任何入口访问它 → 无从执行检索

**没有把握时不要写。** 缺口清单短而准，比长而杂有用；可疑的现象在报告里用一句事实陈述带过即可。

## 输出格式

写入 `<运行目录>/rag-profile.json`：

```json
{
  "version": 1,
  "step": 1,
  "discovered_at": "<ISO 8601 时间>",
  "workspace": "<被测工作区绝对路径>",
  "output_dir": "<运行目录绝对路径>",
  "vector_stores": [
    {
      "kind": "<向量库类型，无法判断时填 unknown>",
      "path": "<相对被测工作区的路径>",
      "verification": "file_structure_only",
      "collections": [
        { "name": "<集合名>", "path": "<集合在库内的路径，无则为 null>" }
      ]
    }
  ],
  "chains": [
    {
      "id": "<kebab-case 唯一标识，由入口与参数组合推导>",
      "origin": "observed",
      "entry": { "file": "<相对路径>", "symbol": "<函数或类名>", "line": 0 },
      "params": {},
      "signature_defaults": {},
      "vector_store": "<对应 vector_stores 中的 path>",
      "collections": ["<集合名>"]
    }
  ],
  "gaps": [
    {
      "item": "<缺失的东西>",
      "impact": "<影响>",
      "needed": "<需要什么来补全>"
    }
  ],
  "open_questions": []
}
```

字段说明：

| 字段 | 说明 |
|---|---|
| `verification` | 本步恒为 `file_structure_only`——仅按文件结构判定，未用对应程序库打开。第②步打开后再升级该值 |
| `origin` | `observed`（工作区调用点中找到）或 `reachable`（仅公开签名可达） |
| `params` | 实际调用时使用的参数值。无法确定时留空对象，不要猜 |
| `signature_defaults` | 签名上的默认值。与 `params` 不同时必须都填，这是两条不同链路的证据 |
| `gaps` | **只收"跑不出指标"的缺失。** 判据见下节，不要按"缺了什么"来填 |
| `open_questions` | 仅用于**阻塞性**问题。本步通常为空数组，链路选择不属于这里 |

## 完成后

向用户报告以下三项，然后停下：

1. 找到的候选链路（入口、参数、对应集合）
2. 存在性缺口及其影响
3. 需要用户回答的阻塞性问题（通常没有）

结尾按 SKILL.md 的「每步的收尾」写。例如：

> 以上是清点结果。请确认候选链路与缺口是否符合预期；如果确认无误，下一步我会打开向量库做一次轻量清点——每个集合大概有多少内容、都是些什么——然后请你确认要评测哪几条链路。需要推进吗？
