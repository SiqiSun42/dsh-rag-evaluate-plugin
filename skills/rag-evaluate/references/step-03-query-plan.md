# 第③步：确认查询计划

## 目标

确定评测集要模拟的两件事，各自带比例：

1. **方向**——问什么（如 安装步骤、故障排查、保修政策……）
2. **形态**——怎么问（自然语言问句、关键词组合……）

两者**相互正交**：形态管"怎么说"，方向管"问什么"。同一个方向可以用不同形态提问，因此两轴各有一套独立的权重。

**本步不生成任何题目，也不生成问法样例。** 具体样例属于后续步骤的校准环节。

## 本步不做的事

- 不生成**成批的**题目或供校准用的样例（后续步骤）。形态清单里每项附一个说明性例子是本章节的要求，不算越界
- 不冻结规格、不定规模（第④步）
- 不生成评测集（第⑤步）
- 不评价被测系统（第⑥步）

## 前置：从样本池归纳方向

读取第②步落盘的 `corpus-sample.jsonl`。

**1. 剔除低质量内容。** 目录页、页眉页脚、版权页、纯符号块等对出题没有价值。第②步已给出噪声启发式与未覆盖的噪声案例，可直接沿用并补充。

**2. 归纳方向，上限 10 个。**

- 每个方向给一句说明，让用户看懂你指的是什么
- **不超过 10 个，这是硬上限。** 语料窄的时候更少也没关系
- 方向应当来自实际样本，不要凭空补充语料里没有的内容

**3. 样本池不足时如实说明。** 如果剔除噪声后剩下的内容归纳不出 5 个方向，直接告诉用户样本不够，并请他补充他知道的线上方向——他可能比样本更清楚用户会问什么。

## 确认一：方向

**一次呈现，一次回复。**

呈现内容：

- 方向清单，每条带编号和一句说明
- 一句提问，包含两个意思：
  - 哪些是线上**最常见**的（可多选）
  - 是否还有可能出现**其他**方向，有就补充

用户回复后，主次自然就分开了：他勾选的是主方向，补充进来的是其他方向。

**不要要求用户标百分比，也不要让他排序。** 他只需要做"选"。

## 确认二：形态

**形态是全局的，不按方向分别定。**

**呈现方式很关键：不要只给类别名。** "自然语言问句""口语化简问"这种标签并排放在一起，用户看不出区别，只会困惑。

正确做法是**拿同一段语料内容，用各种形态各写一条**——例子在前，类别在后：

```
同一个问题的几种问法（下方为格式示例；实际必须取自本库语料）：

  产品质保期是多久？          （自然语言问句）
  质保期多久                  （口语化简问）
  质保期 更换                 （关键词组合）
  质保期 warranty             （术语短语）
```

要点：

- 例子必须**用被测语料的真实内容写**，不要用"某种能力具体怎么运作"这类占位说法
- **同一个内容配多种问法并排展示**，差别才看得出来。各举各的例子反而看不出对比
- 类别名放在例子后面，用来给这一组命名

然后再问用户：哪些是他线上常见的，可多选；并同样问一句"其他可能出现的问题形态"。

**每个形态给一个例子就够，不要生成一批题目。** 成批的、用于校准生成倾向的样例属于后续步骤。

## 比例推导

**不要求用户计算比例。** 按下面的规则自动推导，再呈现给他看：

```
主  方向/形态：均分 90%
其他方向/形态：均分 10%
没有"其他"时：全部均分 100%
```

例如主方向三个 → 各 30%；另补两个其他方向 → 各 5%。

两个轴各自独立套用同一规则。

## 确认三：汇总

把所有推导结果一次性呈现，**尽量简洁**——用户应当一眼看出哪里不对。

```
方向
  安装步骤  30%   ██████████████
  故障排查  30%   ██████████████
  保修政策  30%   ██████████████
  配件更换   5%   ██
  退换流程   5%   ██
  推导：主方向均分 90%，其他均分 10%

形态
  自然语言问句  60%
  关键词组合    30%
  术语短语      10%
  推导：同上

  要改哪个直接说。
```

同时提示**可报告性**：按当前比例，尾部方向在最终评测集的规模下可能只能合并报告，不会有独立的数字。具体到第④步定了规模才能算准，此处只需提醒。

## 松散调整

用户可能反复修改比例，也可能顺手给一些具体示范。

- **比例可以反复改。** 每改一次重新呈现汇总，直到用户确认
- 用户给出的**真实查询样例**要记录进 `user_provided_queries`——它们的可信度高于生成样本，后续步骤会用
- 若用户主动提到"某些情况线上不会出现"，记入 `excluded`

这些自由交互**不计入确认次数上限**。

## 上限

| 项 | 上限 |
|---|---|
| 方向 | 5–10 个，绝不超过 |
| 形态 | 不超过 4 种 |
| 确认交互 | 3 次（松散调整不计） |

到达上限就停，不要继续深挖。

## 输出格式

写入运行目录的 `query-plan.json`：

```json
{
  "version": 1,
  "step": 3,
  "planned_at": "<ISO 8601 时间>",
  "workspace": "<被测工作区绝对路径>",
  "output_dir": "<运行目录绝对路径>",
  "sample_source": {
    "file": "corpus-sample.jsonl",
    "used": 0,
    "excluded_as_noise": 0,
    "exclusion_rule": "<剔除了什么>"
  },
  "topics": {
    "selection": { "primary": [], "secondary": [] },
    "split_rule": "primary 均分 90%；secondary 均分 10%",
    "weights": {},
    "descriptions": {},
    "user_edited": false
  },
  "query_styles": {
    "selection": { "primary": [], "secondary": [] },
    "split_rule": "primary 均分 90%；secondary 均分 10%",
    "weights": {},
    "descriptions": {},
    "user_edited": false
  },
  "user_provided_queries": [],
  "excluded": [],
  "open_questions": []
}
```

字段说明：

| 字段 | 说明 |
|---|---|
| `selection` | 用户勾选的主方向/主形态，以及补充的其他项。**保留原始选择**，不要只存推导后的权重 |
| `split_rule` | **实际生效的**推导规则，不是那个默认值。默认是"主项均分 90%、其他均分 10%"，但用户一旦做了别的选择——要求某些项不计权重、直接指定比例、或不要"其他"这一类——这里就要改写成实际用的规则。**留着默认值会让人按记录复算出与 `weights` 不符的结果** |
| `weights` | 推导出的比例，两轴各自求和为 1 |
| `descriptions` | 每个方向/形态的一句说明，供后续步骤理解标签含义 |
| `user_edited` | 用户是否改动过推导值。改动过则 `weights` 不再等于按默认规则推导的结果，此时 `split_rule` 必须同步改写 |
| `user_provided_queries` | 用户在松散交互中给出的真实查询，原样记录 |
| `excluded` | 用户明确说线上不会出现的查询类型 |
| `open_questions` | 仅阻塞性问题 |

**顶层字段集合固定，不要新增。**

## 完成后

向用户报告以下四项，然后停下：

1. 方向清单、比例及其推导依据
2. 形态清单、比例及其推导依据
3. 可报告性提示（哪些方向可能只能合并报告）
4. 需要用户回答的阻塞性问题（通常没有）

结尾按 SKILL.md 的「每步的收尾」写，并且**必须明确问一句、等用户回答**：

> 这个方向和比例可以吗？如果确认无误，下一步我会把它写成一份标准化的规格文件——定下评测集的规模、判定标准和生成设定。需要推进吗？

**在用户明确表示"可以、开始规范化"之前，不要动手写规格文件。**

本步是松散的确认过程，用户可能还想再改比例；第④步是有固定格式的规范化产物。两者不能混着做——否则"版本号"就失去意义了：改的是草稿还是规格，分不清。
