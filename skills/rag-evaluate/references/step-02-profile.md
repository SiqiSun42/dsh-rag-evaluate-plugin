# 第②步：探测画像

## 目标

在第①步清点出的链路基础上，实际接触被测系统，得出三件事：

1. 运行环境是否可用
2. 向量库的规模、维度、嵌入模型、内容主题与质量缺陷
3. 被选中链路的可调用性与返回值形态

与第①步的根本区别：**第①步只读文件，本步要执行被测代码。**

## 本步不做的事

- **不评价检索结果好不好。** 本步没有评测集，谈不上质量。调用入口只是为了做一次烟测并看返回值的**形态**。
- **不测量分数分布、不做域内/域外对比、不判断阈值是否有效。** 这些是第⑦步用评测集跑出来的结论。
- **不调查任何异常的原因。** 发现可疑现象就记录并提示用户，原因分析属于第⑨步。
- 不确认查询形态与方向（第③步）、不冻结规格（第④步）、不生成评测集（第⑤步）。

## 前置一：确认运行环境

被测系统的运行环境由用户提供。**插件不主动去机器上别处找，也不默认复用任何已存在的环境。**

**只在被测工作区内找候选**：`.venv/`、`venv/`、`env/` 等环境目录，或 `requirements.txt`、`pyproject.toml`、`environment.yml` 等依赖声明文件。

- 找到唯一候选 → 与用户确认后使用
- 找到多个 → 让用户选
- 没找到，或找到但依赖不全 → **停下**，报出缺什么，并给出两个选项：
  - 由插件代为安装（**需用户明确同意**）
  - 由用户自行安装，装完再继续

**绝不未经询问就安装任何东西。** 即便获准安装，也只装进工作区内的环境。

依赖自检的方式：在该解释器里尝试导入被测入口所需的模块，报出缺失项。需要哪些模块，可从入口文件与依赖声明中的 import 语句得出。

选定的解释器路径记入画像，后续步骤沿用。

## 前置二：轻量清点

**目的**：让用户有依据地决定要评测哪些链路。用户看不到内容，就没法选。

**只做下面这些，做完立即交付用户确认，不要继续往下做。**

| 做 | 说明 |
|---|---|
| 打开向量库 | 用第①步确认的环境，得到的 `verification` 升级为 `opened` |
| 列出每个集合 | 名称、条目数、维度 |
| 每个集合瞄 2–3 条原文 | 让用户对内容有直观感受，附在呈现里 |

**明确不做**（这些属于下面的深度画像）：

- 不抽样成池、不写 `corpus-sample.jsonl`
- 不统计重复度、长度分布、噪声占比
- 不归纳内容主题
- 不加载任何模型
- 不调用查询入口

**做完就停，把结果呈现给用户，等回答。** 轻量清点很便宜，但它是"问用户之前"和"问用户之后"的分界线——越过它继续做，就变成替用户决定了他还没决定的事。

## 前置三：确认要评测哪些链路

第①步枚举的是全部可达链路，本步只探测用户选中的那些。此时用户已经知道每个集合装了多少东西、大致是什么内容，可以据此判断。

向用户展示候选项，并标注两条参考信息：

- 该链路在工作区中是否被实际调用（`origin`）
- 静态可判断的成本差异，例如某条路径会额外加载重排模型

用户可以全选，也可以只选一部分。**未选中的链路仍完整保留在画像中，只是标记为未选中**，第⑦步之前还可以改主意。

用户表示无所谓时，默认选中 `origin` 为 `observed` 的链路——那是工作区实际使用的，最接近线上行为。

## 前置四：确认严格按当前系统测评

向用户确认一次：

> 将**严格按当前系统**进行测评——不改写查询、不调整参数、不改阈值、不注入模型推荐的前缀、不补后处理。结果是系统当前的实况，改进建议留到第⑨步。

**这里的「当前系统」指的是接入层背后那一段。** 如果被测项目里还有上游的查询改写、或下游的结果过滤与答案生成，**当作它们不存在**——只测你指定的那个查询入口本身。否则测出来的不是同一套东西，也没法和报告里的建议对上。

确认结果记入画像。用户若希望先改系统，则停下，等改造完成后再开始新一轮运行。

## 产出接入层

本步的产物之一是运行目录下的接入层——被测系统的统一入口，第⑤步之后都复用它。

### 第一选择：声明式（默认）

能用声明描述就不用写代码。声明需要描述四件事：怎么调用入口、怎么切分返回值、分数在哪里、什么表示没有结果。

规格写入运行目录的 `adapter-spec.json`，由插件自带的执行器运行：

```
# 单条
<被测系统的解释器> <插件目录>/python/executor.py \
    --spec <运行目录>/adapter-spec.json --query "<查询文本>" --k <条数>

# 批量：每行一条查询，同一进程内执行，被测模型只加载一次
<被测系统的解释器> <插件目录>/python/executor.py \
    --spec <运行目录>/adapter-spec.json --queries <查询文件> --k <条数>
```

**`<插件目录>` 怎么定位**：加载本 skill 时会给出资源目录，形如 `.../dsh-rag-evaluate-plugin/skills/rag-evaluate/`。插件目录就是它**向上两级**。不要在被测工作区里搜索执行器——它在插件包里，不在工作区里。

执行器是纯标准库脚本，可以用任何 Python 3 运行；但**调用被测入口时必须用被测系统自己的解释器**，因为要导入被测代码及其依赖。

若沙箱不允许访问插件目录，可把执行器复制到运行目录再运行，并在画像里注明这是副本及其来源。

单条输出一个 JSON 对象；批量输出 JSONL，每行一个。**批量必须用 `--queries`**——每次调用都是一个新进程，逐条调用会让被测模型反复加载，实测单条加载开销可达数秒。

执行器输出含 `query_sent`、`raw`、`items` 与 `diagnostics`。它不包含任何针对具体系统的逻辑，全部信息来自声明。

**没有 Agent 写的代码，就没有"顺手优化"的位置。**

支持的返回形状：拼接字符串、结构化列表、纯字符串列表、被字典包裹的返回值（用 `select` 取子值）。完整字段见 `python/executor.py` 的文档字符串。

**必须检查 `diagnostics`：**

| 字段 | 异常含义 |
|---|---|
| `separator_found` 为 `false` | 声明的分隔符在返回值里不存在，`items` 会是"整段文本算一条"，指标将失真 |
| `score_parse_rate` 明显低于 1 | 分数正则没匹配上，分数不可用 |
| `reassemble_ok` 为 `false` | 切分过程丢了内容 |
| `empty_matched` | 本次是无结果，不是解析失败 |

另注意 `result.trim` 默认为 `none`——只剥离声明过的片段，其余逐字保留。需要裁剪正文首尾空白时必须显式声明 `"trim": "whitespace"`。

### 第二选择：代码适配器

返回格式确实不规整、声明描述不了时，才允许写代码。此时必须满足下面的保真度要求。

### 保真度：镜像，不是净化

**被测系统原有的机制一律保留**——前缀、top_k、fallback、去重、重排、截断，有就有，没有就没有。

- **不添加**：不改查询、不加前缀、不调参数、不补后处理、不重排、不去重
- **不删除**：不因为某个机制"看起来多余"就去掉它；系统返回的陈旧结果、可疑 fallback、错误前缀都不属于要修的问题

系统的行为哪怕看起来是错的，也要原样呈现——那正是要被测出来的东西。

若被测入口只返回拼接后的字符串，接入层需要拆开并补齐能补齐的字段；拆不出来的（例如没有文档标识）如实留空，**不要编造**。

### 代码适配器的校验

代码适配器每次返回三样东西：

- `query_sent`：实际发给入口的查询字符串
- `raw`：入口返回的原始值，未经任何加工
- `items`：解析后的条目

两条机械校验，都必须通过：

1. `query_sent` 与插件给定的查询**逐字相同**
2. 按声明的解析规则把 `items` 重建回去，**逐字等于** `raw`；`raw` 命中声明的"无结果"形式时，`items` 必须为空

> 第 2 条的含义：把分数前缀从正文里拆出来放进 `score` 字段属于正当解析，重建时要按同样的规则加回去。反解析对不上，说明适配器添加或删除了内容——必须修正后才能继续。

### 冻结

接入层计算指纹并写入产物。**指纹变化后，此前基于它产生的下游产物全部失效**，需要重跑。

这一条主要防的是一种情况：跑到第⑦步发现分数难看，回头去"修一下接入层"。那时改动会立刻可见，且有后果。

### 生命周期

接入层是每次运行独立的产物：

- 用户选择「接着某次运行继续」→ 复用该次运行目录里已有的接入层
- 用户选择「新建一次运行」→ 重新生成，不继承旧版本

### 兼容补丁

**与接入层是两件事，不要混为一谈。**

接入层是"把返回值翻译成结构化"，总是需要；兼容补丁是"让根本跑不起来的系统跑起来"，属于例外。

当被测入口**根本无法运行**时（导入失败、缺少必要参数、在不存在的路径上操作等）：

- 先停下，向用户说明具体报什么错
- 用户同意后，才可打**最小补丁**，只做让它能跑起来所必需的事
- **不得添加任何额外内容**；返回结果不好看**不算**理由
- 补丁内容写入产物
- **能通过烟测就不打补丁**

## 深度画像

以下探测只针对**被选中链路涉及的集合**。未涉及集合在轻量清点里已经有名称与条目数，不再付出深度成本。

### A. 向量库

- **规模**：条目数（轻量清点已得，此处确认为实测）
- **维度**：优先直接读取；只能反推时标注依据
- **嵌入模型**：以查询代码中的声明为假设来源
- **内容主题**：抽样后归纳，结果需用户确认
- **质量体检**：
  - 是否含可用于溯源的元数据
  - 集合之间的标识空间是否重叠
  - 近似重复内容的占比（切分带重叠窗口时尤其明显）——**连同判定方法一起记录**，否则换次运行数字对不上也无法解释
  - 长度分布、过短条目占比
  - 疑似目录、页眉页脚等噪声内容——**连同判定用的启发式一起记录**

### B. 烟测选中的查询链路

对每一条被选中的链路做一次**烟测 + 形态判定**，到此为止。

**烟测三分：**

| 结果 | 处理 |
|---|---|
| 调用抛异常 | 停下 → 走上文「兼容补丁」流程 |
| 能调用，但返回全空或完全乱码 | 询问用户是否加载了正确的向量库；说明可以继续但意义不大，**由用户决定** |
| 能调用，返回内容有意义 | 继续，不再多问 |

"有意义"的判据：返回的是可读文本、与查询同语种、且不是空串或纯符号。

**形态判定**：能否结构化、是否含文档标识、是否含分数。同时记录单次调用耗时。

**不要评价结果好不好。** 返回值里的片段是否相关、看起来准不准，本步一律不作判断——没有评测集，这种判断没有依据，而且会引出本步不该做的调查。看到可疑内容，记一句事实即可，例如"抽样查询返回的片段与查询主题的关联看起来不明显"，然后继续。

每条链路的探测结果与耗时分别记录，不要混在一起。

### C. 模型一致性

默认以查询代码的声明为假设，**只在出现异常信号时才验证**：

- 维度不匹配
- 抽样内容与查询语言或主题明显不符

验证方法：取库内一条向量，用假设的模型重新编码同一文本，比较余弦相似度。

> 注意：检索分数分布异常集中**不再是本步的触发信号**——那属于第⑦步的测量范围。

## 抽样与落盘

- **抽样前必须先近似去重。** 切分带重叠窗口时相邻条目大量重复，直接随机抽样会反复命中同一段内容，得出错误的内容画像。
- **不要把全部条目交给 Agent。** 统计在脚本里完成，只把摘要和少量样本带回来。
- **样本必须落盘。** 抽样得到的文本写入运行目录的 `corpus-sample.jsonl`，每行一段：

  ```json
  { "id": "<块标识，无则为 null>", "text": "<正文>", "score": null,
    "chain": "<取自哪条链路>", "noise_suspect": false }
  ```

  后续步骤要据此归纳主题方向、挑选代表内容，所以样本是**证据**，画像里只记结论——**不要把样本正文塞进画像**。
- 采样方式、种子与条数记入画像的 `corpus_sample`。同样的输入应当能抽出同样的样本，否则两次运行的结果无法解释。

## 与用户确认

内容主题的归纳结果需要用户确认，并展示少量抽样原文作为判断依据。

字段说明：

| 字段 | 说明 |
|---|---|
| `adapter.mode` | `declarative`（声明式，无 Agent 代码）或 `code`（代码适配器，须通过保真度校验） |
| `adapter.spec` | 声明式：规格文件在运行目录中的文件名。代码式：`null` |
| `adapter.path` | 代码式：适配器文件名。声明式：`null` |

| `environment.created_for_this_run` | 本次运行是否新建了环境 |
| `environment.install_consent` | 用户同意安装时的原话或简述；未安装则为 `null` |
| `environment.details` | 本步职责内的补充事实，如依赖版本、模型本地缓存情况 |
| `corpus_sample` | 样本池的元信息。**样本正文在 `corpus-sample.jsonl` 里**，画像只记采样方式、种子、条数与取自哪些链路 |
| `selected` | 用户是否选中本次要评测。未选中的链路仍保留在画像中，探测字段留 `null`——**不要因为没选就删掉它** |
| `smoke_test` | `ok`（通过）或 `degraded`（全空/乱码，用户选择继续）；未选中的填 `null` |
| `verification` | 本步应升级为 `opened`——已实际打开 |
| `dimension_source` | `measured`（直接读出）或 `inferred`（反推，需写明依据） |
| `embedding_model_source` | `read_from_code`、`verified`（重编码验证通过）、`assumed`（未验证） |
| `capabilities` | 三态 `true` / `false` / `null`，含义是**能否以可编程方式取得**。仅以文本形式嵌在返回值中的不算 `true`，用 `notes` 说明 |
| `notes` | 能力判定或烟测中的例外情况 |
| `gaps` | **只收"跑不出指标"的缺失。** 判据同第①步：没有它，能不能对**当前的系统**跑出指标？只影响"改完之后再测"的能力（重建、对照实验）不算缺口；阈值失效、召回低、结果不相关是第⑦步要测出来的结论，也不算。**写入前把第①步留下的条目按本判据重新过一遍**：不符合的直接删掉，不要标注"不阻塞"后保留——`gaps` 是给下游看的契约，混进非阻塞项它就失效了 |
| `quality` 各项 | 无法测得的填 `null`，不要用 `0` 冒充 |

**顶层字段集合是固定的，不要新增。** 各分节内可以补充属于本步职责的细节（例如 `environment.details`）；若要新增顶层字段，先确认它确实是本步该产出的东西——多半不是。

## 完成后

向用户报告以下六项，然后停下：

1. 运行环境与依赖自检结果
2. 向量库概况（规模、维度、嵌入模型）及其来源
3. 内容主题的归纳结果（附少量抽样原文，请用户确认）
4. 各选中链路的烟测结果、返回值形态与耗时
5. 接入层的方式（声明式/代码）、指纹，以及是否打过兼容补丁
6. 能力缺口及其对后续评测的影响

**报告里不要出现原因分析。** 如果探测过程中发现了可疑现象，用一句事实陈述带过（例如"抽样查询的返回片段看起来与查询主题关联不明显，本步不作判断"），不要展开任何调查。

> 请确认上面的内容主题归纳。如果确认无误，下一步是确认查询计划——评测集要模拟哪些问题方向、用什么问法提问，以及各自的比例。需要推进吗？
