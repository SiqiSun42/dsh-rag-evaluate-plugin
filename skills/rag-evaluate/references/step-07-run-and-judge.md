# 第⑦步：执行与判定

## 目标

对评测集执行检索、判定相关性、计算指标。

三段严格分开：**执行检索 → 判定 → 聚合**。中间各自落盘，后面的段可以独立重跑。

## 前置

- 运行目录中已有 `eval-set.jsonl` 与 `spec.json`

## 本步不做的事

- **不改规格**（回第④步）、**不改评测集**（回第⑥步）
- **不调查异常原因**（第⑨步）。判定过程中看到可疑现象，记一句事实，不要展开
- **不修改被测系统**，也不因为结果难看而调整任何参数

## 第一段：开跑前必须停下确认

**这一步会连续调用被测系统 N 次，中途不再询问。** 开跑前把下面几件事说清楚，并等用户明确说"开始测评"：

```
评测集共 N 条（<M> 个方向 × <K> 种形态）
  · 将对每条题目调用被测系统一次，共 N 次
  · 判定约 P 个「查询 × 返回块」的组合
  · 预计耗时约 X 分钟（按实测单条 Y 秒外推，不要拍脑袋）
```

三件事必须确认：

1. **评测集确认过了吗**——第⑥步末尾问过；没问过就先让用户过目
2. **用户明确表示现在开始测评**——只是"评测集没问题"不等于同意开跑
3. **判定用哪个模型**（见下）

### 判定模型

**用当前 DSH 会话配置的模型**，插件不自己选、也不管理凭据。开跑前告诉用户一句：

> 判定会用当前 DSH 配置的模型（`<模型名>`）。想换的话，先在 DSH 里改模型与 API 配置——**包括用本地模型**——再回来开始。

**顺带提示一处偏差**：第⑥步生成题目、第⑦步判定相关性，如果用的是同一个模型，存在**自评偏差**。想降低它，最直接的做法是在两步之间换掉 DSH 的模型配置——**生成用一个，判定用另一个**。是否要这么做由用户决定，不要替他决定。

## 第二段：执行检索

**用接入层的批量模式跑，不要逐条调用。** 逐条调用每次都是新进程，被测模型会反复加载。

结果写入 `raw-results.jsonl`，每行一条：

```json
{ "case_id": "q001", "chain": "<链路 id>", "query_sent": "<实际发出的查询>",
  "results": [ { "rank": 1, "text": "<块正文>", "score": 0.62 } ],
  "error": null, "latency_ms": 0,
  "spec_version": "1.0", "adapter_hash": "<接入层指纹>" }
```

- `query_sent` 必须是**原样发出去的查询**，不做任何变换
- `results` 里保留原始顺序与分数，不要重排、不要过滤
- 出错的条目记进 `error`，**不要丢掉**——它是结果的一部分
- **原始结果一经产生即不再改动**，是后续一切结论的证据

这一段**只跑一次**。以后改判定标准只重跑第三段。

## 第三段：判定

### 判定单位是"查询"，不是"查询 × 块"

一次请求里给出该查询的**全部候选块**，让判定者逐个打分。这样问题和答案要点只出现一次——按对判的话要重复两三遍。

### 判定标准来自规格

用 `spec.scoring` 里的 `rubric`、`hit_definition`、`unanswerable_policy`，**不要自己发挥**。判定结果是**分级相关性**，不是简单的命中/未命中。

**把源块和答案要点一起交给判定者。** 要点可能经过整理、带指代（例如"这种形态下…"），单看要点判不准；源块在手里，指代才能消解。

### 分片并发，子代理直接落盘

按查询分片，每片 20–30 条。用 subagent 或 workflow 并发。

**每个子代理把判定写进自己的文件，只回一行摘要**（判了多少条、各档多少）。

**明细不要回主 Agent**——几百条判定的正文加起来会把主上下文吃掉，而主 Agent 并不需要看它们。

### 判定结果落盘

写入 `judgments.jsonl`，每行一个「查询 × 块」的判定：

```json
{ "case_id": "q001", "rank": 1, "score": 2, "note": "<可选，一句话以内>" }
```

- `score` 按规格的分级口径（例如 0=无关 / 1=部分 / 2=完全）
- `note` **限一句话以内**。它是给抽查用的，不是给分析用的——写长了输出本身就是几万 token
- 无法回答的条目按规格的 `unanswerable_policy` 单独判定（通常是"返回空结果算对"）

### 只判一次

**全部指标由同一批判定推导**，不要为每个指标单独判一遍。否则成本成倍，而且不同指标基于不同判定，出现矛盾时没法解释。

## 第四段：聚合指标

从 `judgments.jsonl` 推导全部指标，写入 `metrics.json`。

**只算规格里声明可算的指标**，不可算的照原样保留 `unavailable` 与原因——**不要用近似值补**。

按规格的层级输出：总分、按方向、按形态、按格子（只对规格里标为可单独报告的那些）。再单列无法回答样本的拒答正确率。

**这一段是纯计算，适合写成脚本。**

## 省时间和 token 的做法

| 做法 | 省的是什么 |
|---|---|
| 子代理直接落盘、只回摘要 | **最大的一项**：明细不进主上下文 |
| 判定按查询分组 | 问题和要点不重复出现 |
| 分片并发 | 时间 |
| 判定只回结构化结论，理由限长 | 输出 token |
| 检索只跑一次 | 改判定标准时不用重新加载被测模型 |
| 判定结果以「查询 + 块 + 规格版本」为键缓存 | 重跑同一套评测时直接复用 |

## 输出格式

`raw-results.jsonl`（第二段）、`judgments.jsonl`（第三段）、`metrics.json`（第四段），格式见上文。

**顶层字段集合固定，不要新增。**

## 完成后

向用户报告以下四项，然后停下：

1. 跑了多少条、其中多少条出错或返回空
2. 判定规模（多少个「查询 × 块」），以及判定用的模型
3. 指标概览：总分、按方向、按形态；以及哪些层级按规格只作参考
4. 无法回答样本的拒答正确率

**报告里不要出现原因分析。** 看到可疑现象用一句事实带过，归因属于第⑨步。

结尾按 SKILL.md 的「每步的收尾」写。例如：

> 测评已跑完，共 N 条。指标概览如上，判定用的是 <模型名>。请看一下有没有明显不对的地方；如果没问题，下一步是效度校验——确认这批数字可信、以及有没有哪里跑偏了。需要推进吗？
