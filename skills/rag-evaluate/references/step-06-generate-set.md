# 第⑥步：全量生成

## 目标

按**已冻结的规格**生成完整的评测集。

规格定好了方向、形态、比例、规模、判定口径；第⑤步确认过的样品定好了风格。本步把它们变成几百条具体题目，**不重新讨论规格，也不重新打样**。

## 前置

- 运行目录中已有 `spec.json` 与 `samples.jsonl`
- 第⑤步的样品已获用户确认
- **用户已同意开全量**（见下，这不是同一件事）

## 本步不做的事

- **不改规格。** 发现方向或形态本身有问题，回第④步提升版本号
- **不评价被测系统。** 不对生成的题目做检索验证（第⑦步）
- 不重新抽素材（第⑤步）、不重新打样（第⑤步）

## 第一段：开跑之前必须拿到用户点头

**这一步会跑很久**——通常几百条，还要逐条校验。开跑前明确告诉用户预计规模，并等他同意。

**确认过样品不等于同意开全量。** 样品是十几条，全量是几百条，代价不在一个量级。说清楚预计条数与大致耗时，再开始。

## 第二段：生成

### 按规格生成，不是按样品生成

**规格里每一个格子都要出题，一条都不能少。** 这是本步最容易犯的错——样品只覆盖了一部分格子，顺手就按样品铺开了。

```
生成依据 = spec.size.cells（方向 × 形态 × 条数）
样品     = 只提供风格范例，不决定生成哪些格子
```

- **覆盖规格里的全部方向和形态**，按 `size.cells` 逐格出题
- **样品里没有的方向或形态，照样要生成**——它在规格里有配额
- `spec.size.unanswerable` 单列，不占任何格子，**每条注明"为什么库里没有"**

### 怎么分片

按 `spec.size.cells` 分片，每片一个（方向 × 形态）组合，生成该格声明的条数。素材取自 `corpus-source.jsonl`。

**每片发给生成者的东西完全一致**：

- 规格里相关的约束（方向说明、形态说明、`generation.constraints`）
- 用户确认过的样品作为范例，**连同它们的 `note`**
- 该格要出的条数
- 对应的素材块

条目多时用 subagent 或 workflow 分片并发，主 Agent 只做校验与汇总——逐条写进上下文很贵。

## 第三段：校验与落盘

**校验适合写成脚本**，它全是确定性的检查：

- **各格条数与 `spec.size.cells` 逐格一致**——特别是那些没有样品的格子，重点核对它们一条不少
- 每条的形态与它所在格子的声明一致
- 可回答的题目都有源块；**源块不重复**（同一块只出一道题）
- `answerable: false` 的条目确实不指向任何源块
- 总数 = 各格之和 + 无法回答数

**再算一遍泄漏检查**：对全量条目算 query 与源块的 n-gram 重合度，**和打样时的分布对比**。明显变差说明分片生成跑偏了，要回去处理分片指令。

### 要点与源块的一致性筛查

算每条要点与它源块的**最长公共子串比例**，把比例明显偏低的那批列出来备查。

**这是筛查，不是判定，更不是"比例低就改"。** 低比例有两个来源，处理完全相反：

| 来源 | 处理 |
|---|---|
| 源块本身**可读性不高**（图片、表格或其他特殊格式没有被正常解析），要点是从它整理出来的 | **已知的预处理缺陷**（第②步质量体检已记录）。评测阶段无解，**不改**——它属于第⑨步「内容对但切分不当」那一类失败 |
| 源块是正常散文，要点却几乎不重合 | **可疑：要点可能是编的**。逐条对着源块核，编的删掉重出 |

分辨两者只需看一眼源块本身：排版读不通、结构错乱的，是前者。

**可读性差的重排是正常的，改掉反而丢了可读性。** 筛查的目的只是把"可能编的"挑出来，不是让要点去对齐原文。

### 为什么要点经过整理，而不是原文摘录

有些源块的**可读性不高**——图片、表格或其他特殊格式没有被正常解析，正文读不通、结构错乱。

**如果要点也照着这种正文摘录，判定就没法回答"库里到底有没有这个内容"**——因为你分不清是**检索没找到**，还是**找到了但块本身就读不通**。两种情况的改进方向完全不同。

把要点整理成可读的话之后，两件事就分开了：

| 观察到的现象 | 归因 |
|---|---|
| 要点被命中，且命中的就是最优块 | **检索没问题**；问题在块本身可读性不高 → "内容对但切分不当" |
| 要点找不到，而对应源块的排版本身正常 | **检索的问题** |

**整理要点既不修改源块，也不修改向量库。** 它只把判定从"字面对不对"变成"内容对不对"，让上面这两行能区分开。

库的问题归第⑨步建议"重新处理语料"，检索的问题归第⑨步提优化方向——两者不是一回事。

**这份名单留着给第⑧步**——核对要点可靠性时用得上。

校验不通过就修，不要把不合格的条目写进产物。

校验通过后写入 `eval-set.jsonl`。

## 第四段：生成完问一句

> 评测集已生成，共 N 条（各方向各形态都按比例覆盖了）。
> 要先过一遍吗？我可以按方向分组给你一份清单。或者直接开始测试。

几百条逐条看过一遍很累，所以**把选择权交给用户**：他要审查就交付可读清单、有问题就地改；他说直接测就开始。**不要替他决定。**

**审查期间发现的规格问题仍然要回第④步提版本**，不在这一步就地改；只是某几道题写得不好，就地改即可。

## 输出格式

`eval-set.jsonl`，每行一条：

```json
{
  "id": "q001",
  "topic": "<方向>",
  "style": "<形态>",
  "question": "<题目正文>",
  "expected_points": ["<答案要点>"],
  "source_chunk_id": "<源块标识>",
  "answerable": true,
  "origin": "generated",
  "pilot": false
}
```

无法回答的条目：

```json
{
  "id": "u001",
  "topic": null,
  "style": "<形态>",
  "question": "<题目正文>",
  "expected_points": null,
  "source_chunk_id": null,
  "answerable": false,
  "unanswerable_reason": "<为什么库里没有>",
  "origin": "generated",
  "pilot": false
}
```

字段说明：

| 字段 | 说明 |
|---|---|
| `topic` | 必须是 `spec.topics.weights` 里的键。无法回答的填 `null` |
| `style` | 必须是 `spec.query_styles.weights` 里的键 |
| `expected_points` | 判定依据。**来自源块正文，不能凭空写** |
| `source_chunk_id` | 指向 `corpus-source.jsonl` 里的块。源块正文不重复存进评测集 |
| `origin` | `generated`（模型生成）或 `user_provided`（用户给的原始查询） |
| `pilot` | 是否来自第⑤步确认过的样品 |
| `unanswerable_reason` | 仅无法回答的条目需要 |

**顶层字段集合固定，不要新增。**

## 完成后

向用户报告以下三项，然后停下：

1. 实际条数与分格，以及与规格的逐格对照
2. 无法回答样本的条数与它们各自的理由
3. 泄漏检查结果，与打样时的对比

结尾按 SKILL.md 的「每步的收尾」写。例如：

> 评测集已生成，共 N 条，各方向各形态都按规格覆盖到了。要先过一遍吗？或者直接开始测试。两种都行，你说。

**如果用户直接开始测试**，进入第⑦步——对每条题目调用被测系统、判定结果相关性、算指标。
