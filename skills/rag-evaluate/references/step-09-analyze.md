# 第⑨步：归因分析

## 目标

由指标得出结论：**问题在哪一层、下一步该动什么。**

这是九步里唯一出结论的一步。前面八步都在产出数据，这一步把它们变成决策。

## 这一步的输入是数据，不是"刚才那次运行"

分析方法与数据来源无关。**如果有人拿人工测评的结果过来，同样能接在这里**——只要有逐条的判定明细和对应的问题集。

所以下面讲的是**通用的评测数据分析**，不是"插件自己跑出来的数据才适用"。

## 前置

- `metrics.json` 与 `validation.json`
- **效度校验没有失败的项。** 校验不通过就先回去修，不要带着已知缺陷的数据做分析——那只会把缺陷放大成错误的结论

## 本步不做的事

- **不改任何产物，不改被测系统。** 只出结论和建议
- **不实施建议。** 插件给方向和依据；改代码是评测结束之后的事，由用户与 Agent 另行处理
- **不把库的覆盖度当结论。** 那需要知道库里应该有什么，不是本插件能判断的
- **不做超出规格可报告范围的结论**（见下）

## 评判依据：三级阶梯

**报告要回答"好不好"，先得有尺子。** 从 `spec.acceptance` 取；没填就是第三层。

```
第一层  用户给了数值验收线   → 直接答达标 / 未达标
第二层  用户给了偏好型要求   → 按偏好判，并据此定建议方向
第三层  什么都没有           → 相对判定：从最好排到最差
```

第二层的偏好型要求不只是尺子——**它改变建议的符号**：「宁可多返回不可漏」对应降阈值，「宁可少返回不可错」对应升阈值。

### 常识能判什么、不能判什么

- **不能判绝对水平。** RAG 的"合理水平"高度依赖任务、语料与查询形态，没有通用达标线。没有尺子时硬给"好/差"是误导
- **能判结构性异常。** 这些不是分数高低，是明显故障，任何任务下都不正常：空结果率异常高、某条链路或某个方向接近全败、指标之间的关系不成立、全部条目接近满分

**所以：分数高低不靠常识判，结构异常靠常识判。**

## 一、先守住报告纪律

**每个数字都要带样本量与置信区间**，不要只给点估计。`spec.md` 里已经算过分辨率，直接沿用。

**分层结果的报告范围以 `spec.size.reportable` 为准。** 规格里标为"只作参考"的层级，不要拿来下结论——哪怕两格之间差得很大。样本量不够时，差异可能只是噪声。

**均值不够，要报分布。** 平均 0.6 可能是"所有查询都在 0.6"，也可能是"一半满分一半零分"——这两者的改进方向完全不同。至少给出各分层的分布或分位数。

## 二、比较变体：用配对检验

如果评测了多条链路、多种形态，或改前改后各跑了一次：

**同一批问题渲染成不同变体，样本天然配对**——所以用配对检验，不要比较两个独立均值。后者在小样本上极易得出错误结论。

| 数据形态 | 用什么 |
|---|---|
| 二值结果（命中 / 未命中） | 配对检验，如 McNemar |
| 连续指标（nDCG、MRR 等） | 配对 bootstrap，或符号秩检验 |
| 比例类指标的置信区间 | Wilson 区间 |

**同时报效应量，不要只报 p 值。** "差异显著"和"差异值得动手"是两件事。

**做多个比较时要校正**（Bonferroni 或 FDR）。方向一多、变体一多，比较次数会迅速膨胀，不做校正就会挑出纯属偶然的"显著"。

**如果一个变体的每道题都比另一个好，那是真的；如果只是各有胜负，均值差再大也要谨慎。**

## 三、失败案例归因——这是分析的主体

**均值只说明效果不佳，归因才说明该动哪里。** 逐条看失败案例，按下面的判据分类，**给出每一类的占比与代表性案例**。

| 类别 | 判据 | 指向 |
|---|---|---|
| **库 / 切分的问题** | 命中了最优块，但该块本身可读性不高（图片、表格或特殊格式没被正常解析） | 重新处理语料 |
| **检索未召回** | 相关内容确实在库里，但没出现在返回结果里 | embedding、切分策略 |
| **被阈值滤掉** | 召回了，但被阈值剔除——表现为返回空或条数不足 | 阈值设置 |
| **排序靠后** | 召回了，但排在截断范围之外 | 排序、rerank |
| **基准答案有误** | 答案要点与源块对不上 | **评测集的问题，不是系统的问题** |
| **库的覆盖度** | 用户问的某类内容库里确实没有 | 补语料——**顺带发现，不是本次的检测项** |

### 关于「库里没有答案」的那批查询

**检索层没有「拒答」这回事。** 端到端 RAG 里的 Negative Rejection 评的是生成模型有没有选择不答——那有决策成分；而检索层只会因为分数低于阈值而返回空，纯粹是**阈值标定**。

所以这批查询上该报的是 **负样本上的误召回率**（假阳性率），本质是个二分类：

| 系统行为 | 判定 |
|---|---|
| 返回空 | 真阴性（正确） |
| 返回了任何内容 | **假阳性（误召回）** |

**这个率是阈值的函数。** 只报一个点说明不了问题——有条件时应该扫一遍阈值，看误召回率随阈值怎么变，那才能回答「阈值该设多少」。阈值扫描属于诊断，**单独标注，不要混进基线数字**。

**「基准答案有误」必须单独区分。** 不区分就会把评测集的缺陷算到系统头上，然后去改本来没问题的环节。

**「库 / 切分的问题」与「检索未召回」要分清**：前者是命中了但块读不通，后者是根本没命中。前者的建议是重新处理语料，后者才是改检索。

### 症状在哪一层出现，不等于原因在哪一层

**每一层的症状，都要先问一句：上一层已经记录过的缺陷，能不能机械地造成它？**

块被切开、块内没有结构、块从词或数字中间开始——看着都像切分层的症状。但如果画像里已经记录了「表格被抽取时压平成无分隔长串」，那超长段落就是压平的直接产物，硬切只是它的次生结果。**这时要动的是第 1 层，不是切分参数**：在已经压平的文本上，块大小、重叠、「按语义边界切」都无处着力——边界在上游就没了。

**判据：如果修复的前提是「上一层没做某件事」，结论就落在上一层。**

### 发现关联之后，先怀疑它是代理

分组之间「有关联」不足以定因。**先检查这个分组是不是某个更根本属性的代理**——按被怀疑的那个属性再分一次层，看关联还在不在。

例：按「长度接近块上限」分组，该组的漏召率显著更高（p=0.008）。但再按内容形态分层：长正文里的硬切块漏召率并不高于长正文整体，漏召几乎全部集中在表格/清单类的源块上。「硬切」只是「表格被压平」的代理——压平后必然超长，超长必然被硬切。

**两个分组高度重合时，要么用数据把它们分开，要么如实写「本次数据无法分离」，不要只报其中一个。**

### 代理指标不是机制证据

用可测量的东西去代理一个测不到的机制时（例如用「长度接近块上限」代理「被滑窗硬切」），**要么先抽几条实际内容看一眼确认这个代理成立，要么全程写明它只是代理**。

不要给它起一个听起来像机制的名字，然后就当机制用——「满长硬切块」这样的叫法，会让一个还没验证的代理看起来像已经成立的结论。

## 四、判定本身可不可信

看 `validation.json` 里的**目视复核异议率**。

异议率偏高时，说明判定标准本身有问题——**此时不要报告系统的结论**，先回第④步改判定口径重判。判定不可信时，指标再精细也没有意义。

## 五、结论怎么写

**两个层次，不要混在一起：**

**第一层：数据说明了什么。** 完全可追溯——每个数字都能在 `metrics.json` 里找到，每类失败案例都能在 `judgments.jsonl` 里找到实例。

**排序方式**：从最差的指标入手，但**落点按失败归因定**——因为最差的指标未必对应最该动的层（例如未召回里如果有相当比例其实是「库里没有」，那是覆盖度不是检索）。

**第二层：建议做什么。** 每条建议都要注明依据哪个数字、对应哪一类失败案例、**以及它覆盖了多少条失败（分子/分母）**。建议可以分条给优先级，但**不能是模型的自由判断**。

**建议指名的是一个在当前状态下可实施的机制。** 如果这个机制的前提是「上游先做某件事」，那建议要落到上游——例如「先把表格在抽取阶段还原成结构，再谈切分」。

**优先级跟覆盖量挂钩。** 一个统计上显著的关联，如果只覆盖失败总量的一小部分，或者完全覆盖不到最大的那簇失败，就不该排在最高优先级。

**建议里可以引用项目里已有的环节**，例如"项目里已有查询改写环节，可以考虑往那个方向调整"。但**到此为止**——不实施，也不评价那个环节。

### 达标就是结论，不是缺陷

**体检指标有可能完全健康。** 如果系统已经够好——**尤其是用户给过明确指标并且达到了**——那就直接说不用改。

```
各项指标已达到你给出的验收线，本次没有需要修改的环节。
```

**不要为了"报告看起来有价值"而硬找问题。** 编出来的优化点会让用户去动本来没问题的环节，把好的改坏——这比不提建议糟得多。

逐层诊断里每一层照常给结论，只是每一层都会写成「这层不用改」，并各自写明依据。

区别只在有没有尺子：

| 情况 | 报告结论 |
|---|---|
| 有验收线且达标 | **达标，无需修改** |
| 没有尺子，但各项指标彼此接近、无结构性异常 | 各项接近，**但没有验收标准，无法判断是否达到你的要求**——不替用户下"好"的结论 |
| 没有尺子，且存在结构性异常 | 指出异常及其影响 |

**必须写清的三件事：**

- 本次结论依据的是**哪个规格版本**、哪个接入层指纹
- 哪些分层**不能单独下结论**
- 哪些问题**不在本次检测范围内**（库的覆盖度、上游改写、下游后处理）

## 输出格式

写入运行目录的 `report.md`。结构：

```
一、指标总表       ★ 所有指标逐行列出，每行带样本量、置信区间、以及判定
二、分层指标       按方向、按形态、按格子（只报规格允许的层级）；
                   每层标出与总分的差距，明显偏低的单独点名
三、变体比较       （若有）配对检验 + 效应量 + 多重比较校正
四、失败归因       各类别占比 + 代表性案例
五、逐层诊断       ★ 固定的层清单，逐层过一遍，每层都要有结论
六、建议与优先级   每条挂上依据的数字
七、范围声明       规格版本、接入层指纹、不可单独下结论的分层、
                   不在检测范围内的事项
```

### 这是一份体检报告

- **全部指标都要列**，一个不落
- **已经足够好的**：一行带过，说清「这层不用改」及其依据
- **需要修改的**：按**严重程度**和**用户偏好**展开——失败案例、归因、建议方向
- **确实没有可改的**：**直说不用改**。体检指标有可能完全健康——尤其用户给过明确指标并且达到了，那就是本次的结论，不要硬凑问题

### 一、指标总表要完整，并且逐项判定

**把所有指标一次列完，一个不落**（包括不可计算的——那也要列出并写明原因）。每行四样东西：数值、样本量、置信区间、判定。

**判定不能拍脑袋。** 按下面的顺序找依据：

1. **用户在规格里给的目标值**——有目标就按目标判
2. **没有目标时给相对判定**，并写明是哪一种相对：
   - 与总分比，这个分层是明显偏低还是持平
   - 与同类分层比（例如各方向之间）
3. **绝对好坏不下结论**——不同任务、不同语料的合理水平差得很远，没有目标时硬给"好/差"是误导

**不可计算的指标要单独成行说明原因**（例如"入口不返回文档标识"），不要省略——省略了读者会以为没测。

### 五、逐层诊断——固定清单，每层都要表态

**按 RAG 管线的顺序逐层过一遍**，不要只在有问题的地方打转。**没有问题的层也要表态**——否则用户会去优化本来没问题的环节。

| 层 | 这一层看什么 |
|---|---|
| 1 语料与预处理 | 源文档解析质量（图片、表格、特殊格式）、内容是否完整 |
| 2 切分 | 块大小、重叠、语义完整性 |
| 3 向量化 | embedding 模型选型、维度、归一化方式 |
| 4 召回 | 候选数量、召回率——**未召回的失败案例归这一层** |
| 5 重排 | 是否启用、重排阈值——**排序靠后的失败案例归这一层** |
| 6 阈值与空结果 | 相似度阈值、负样本误召回率 |
| 7 查询侧 | 形态适配。**上游若有查询改写，不在本插件范围内，只提示存在** |
| 8 下游 | 后处理、生成。**同样不在范围内，只提示存在** |

每一层给三样东西：

- **现状**：这一层实际是什么配置（来自画像与规格）
- **数据表现**：有没有失败案例指向这一层，占多少
- **结论**：**一句话说清这一层要不要改、为什么**

结论有三种，但**不要用固定的标签词**，按正常说话写：

| 情形 | 怎么写（举例） |
|---|---|
| 有案例支撑要改 | 「这一层建议改：……」「这里可以优化一下，依据是……」 |
| 本次看不出问题 | 「这一层本次不用改：……」「这里暂时不动，因为……」 |
| 本次判断不了 | 「这次数据看不出这一层的问题：……」「要判断这一层，还需要……」 |

**「不用改」和「要改」一样重要，都要给依据**——例如「基准答案有误 0 条、要点编造 0 条，说明评测集本身没问题，不用动它」。

**报告正文里不要出现这些词**：`要动`、`不要动`、`不做判断`、`本插件`、`本步`、`按规格`。它们是给 Agent 看的分类，用户读报告时不需要知道有这套分类——他要的是「这层怎么样、要不要改」。

### 「这层不用改」什么时候算数

**画像里记录过的缺陷，不能因为「本批没有失败案例直接指向」就判它没问题。** 缺陷可能正通过另一个症状在起作用——这正是「症状在哪一层出现，不等于原因在哪一层」要防的事。

只有两种情况能让一层真正免除：

- **证明了它不可能产生观察到的症状**
- **标为待查**，并写清为什么不查

否则那一层只是"本次没测到"，不是"没问题"。

报告**引用** `metrics.json` / `judgments.jsonl` / `validation.json`，不重复存里面的数据。

## 完成后

这是最后一步，不再有"下一步"。报告交付后：

- 把**产物清单**列给用户（运行目录下所有文件）
- 提醒用户：**要改代码的话，那是评测之后的事**，可以让 Agent 按报告的建议继续，但那不属于本插件
- 若用户想保留多版对比，**新建一次运行**，不要在同一次运行里并存

结尾按 SKILL.md 的「每步的收尾」写，但把"下一步"换成可以做什么：

> 报告已生成，在 `report.md`。主要问题是……（一句话）。
>
> （若全部达标，改成：各项指标已达到你给出的验收线，没有需要修改的环节。）
> 如果你想按报告的方向改代码，那属于评测之后的事，我可以另开一轮帮你做——但那不在这个插件的范围内。
