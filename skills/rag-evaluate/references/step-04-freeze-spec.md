# 第④步：冻结规格

## 目标

把第③步已确认的查询计划，连同本步补齐的标准项，固化成一份**带版本、可复现、自足**的规格文件。

规格是评测集可复现性的锚点：半年后有人问"这批题目是怎么来的"，答案应当完全在这份文件里，不需要回头翻对话。

**本步不生成、不执行任何东西。** 它只做整理与冻结。

## 前置：必须有用户的明确确认

- 运行目录中已有第③步的 `query-plan.json`
- **用户已明确表示第③步的草稿可以、同意开始规范化**

第③步是松散的确认过程，本步是有固定格式的规范化产物。**没有那句明确确认就不要开始**——用户可能还想改比例，那时规格还没到该写的时候。

## 本步不做的事

- 不重新讨论方向与形态（那是第③步）
- 不生成任何题目（第⑤步）
- 不执行被测代码，不测任何指标（第⑥步）
- 不评价系统

## 规格的三个组成部分

| 部分 | 来源 | 性质 |
|---|---|---|
| **搬运** | 第③步已确认的方向、形态、比例 | 直接写入，不重新解读 |
| **补齐** | 本步需要决定的标准项：规模与配额、判定标准、生成设定 | 需要与用户确认 |
| **记录** | 自动生成的溯源信息：语料快照、上游指纹、版本与时间 | 自动，无需用户参与 |

## 补齐一：规模与配额

**规模不由向量库大小决定。** 需要多少条测试，取决于要在什么层级上下结论。

```
报告层级 = 方向 × 形态            （交叉后形成若干格子）
每格条数 >= 最小可报告样本量
总量 = 各格之和 + 无法回答的样本（单列配额，不占方向比例）
```

- **最小可报告样本量**：低于它，该格子的数字只在噪声里。把它作为参数写进规格，不要藏在心里。
- **无法回答的样本单列**：它不是某个方向，而是横跨所有方向的一个维度。每条要注明"为什么库里没有"。
- **必须声明哪些分层单独报告、哪些合并报告。** 总量有限时，尾部方向的格子会很薄，与其给出不可信的数字，不如合并。

**分辨率参考**（用于向用户解释规模的意义，按实际样本量重算，不要照抄）：

| 总量 | 总分的置信区间 | 每格（8 格均分） |
|---|---|---|
| 50 | 约 ±13 点 | 不可用 |
| 200 | 约 ±7 点 | 约 ±19 点 |
| 500 | 约 ±4 点 | 约 ±12 点 |

把这组数字写进 `spec.md`，让用户知道自己拿到的是什么分辨率的结论。

### 用户问"语料这么大，几百条够吗"

几乎一定会被问到。**不要让用户一追问就把规模往上加**——那样规模会失控，而且方向是错的。

**规模不随语料大小增长。** 抽样的单位是**查询**，不是文档。要估计的是"系统在用户查询分布上的表现"，不是"每一个内容块的质量"。语料大小只在一处起作用——**上限**：不该生成超过去重后有效块数量的题目。

工业界的实际量级，可以直接引作参照：

| 基准 | 语料规模 | 查询数 |
|---|---|---|
| TREC ad-hoc 经典做法 | 几十万至百万文档 | 约 50 个 topic |
| TREC ROBUST 2004 | 同上 | 250 条 |
| MS MARCO passage | 880 万段落 | dev 约 7000，常用子集数百 |
| BEIR（18 个数据集） | 数万至数百万 | 几十至几百 |
| RAG 工程实践 | — | 100–500 |

用 TREC 举个例子最直观：**用 50 个 topic 对着上百万文档评了几十年，业界公认够用**——前提是 topic 抽得有代表性。

**按目标定规模，而不是按语料：**

| 目标 | 规模 |
|---|---|
| 看系统大致行不行 | 100–200 |
| 变体对比（A/B） | 约 200；配对比较效率高 |
| 每个方向独立出结论 | 300–500 |
| 回归测试、检测小幅改进 | 500–1000，且**固定复用同一套** |

**两个必须主动讲清的限制：**

1. **分辨率。** 明确告诉用户每个层级能分辨多大的差异（用上面的置信区间表），以及哪些格子只作参考、不单独下结论。
2. **我们测的不是 TREC 意义上的召回率。** TREC 用 pooling：把所有参评系统的 top-1000 汇总后人工判定，所以能算"全库相关内容找回多少"。我们只判被测系统自己返回的 top-k，**不知道库里还有多少相关内容没被找到**。所以严格说是**命中率**，不是全库召回。这一条要写进报告，否则数字会被误读。

**最后补两句给用户的话：**

- 覆盖度靠**抽样方式**，不靠数量。200 条均匀覆盖确认过的方向，比 2000 条挤在一个方向上更有代表性。
- 评测集的价值随**复用**增长——同一套题跑改动前后、跑不同模型，比一次性跑 1000 条有用得多。

## 补齐二：判定标准

**这是规格里最关键、也最容易被漏掉的一段。** 判定标准不写死，同一个评测集会跑出不同的数字。

必须明确：

- **判定粒度**：基于答案要点，还是基于文档标识。
  > 切分带重叠窗口时，同一内容存在于多个相邻条目中，按文档标识严格匹配会系统性低估指标。默认按答案要点判定。
- **相关性分级**：二值还是分级（如 0=无关 / 1=部分 / 2=完全）。指标里有归一化折损累计增益之类需要分级相关性的，二值判定会让它退化。
- **指标清单与各自的 k 值**：只列可计算的。
- **每个可计算的指标都要写明口径，即分子与分母各是什么。** 同名指标可以有多种算法；不写清会出现两个看似独立、实则同一个数的指标。典型例子：每题只有一个答案要点时，"命中率"与"召回率"算出来完全相同。不澄清这一点，报告里会多出一个没有信息量的数字，还可能被当成独立证据。
- **不可计算的指标显式标注**：写明是哪一项、为什么不可计算（例如"入口不返回文档标识"）。**不要用近似值替代**。
- **一次判定推导全部指标**：判定只跑一遍，所有指标从同一批判定推导，不逐个指标单独判定。
- **无法回答样本的处理方式**。
- **用户不指定指标时的默认值**：给一份保守默认（可计算的指标全上，不可计算的如实标注），不要给"全套"制造虚假的完整性。
- **判定的执行方式要估代价。** 判定对数量 ≈ 题目数 × 返回条数；这个量级逐条交给 Agent 会吃掉大量上下文。规格里要写明打算怎么执行（批量脚本、子代理分片、或工具批量调用），而不是只写"由 Agent 判定"。

## 补齐三：生成设定

生成评测集所用的模型与参数，写进规格。否则同一份规格换一次生成，结果不同却无法解释。

## 记录项

- **语料快照**：基于哪些集合、各多少条。库变了，规格与据此生成的评测集即失效。
- **上游指纹**：系统画像、查询计划、接入层的指纹。接入层指纹变化意味着下游产物全部失效。
- **版本号与冻结时间**。

## 输出

写成两份**同源**文件，不要手工维护两份：

| 文件 | 读者 | 说明 |
|---|---|---|
| `spec.json` | 程序 | 生成器、校验器、报告引用的是它 |
| `spec.md` | 人 | 从 `spec.json` 渲染，供用户确认与事后查阅 |

`spec.md` 要能用一屏说清：方向与形态的比例、总量与分格、指标清单、判定口径、以及哪些结论能单独下、哪些只能合并。

## 确认与冻结

向用户呈现 `spec.md` 的关键部分，**一次确认**：

> 规格将冻结为 v1.0。方向和比例来自第③步；规模按最小可报告样本量算得；判定标准如下……确认冻结吗？

**冻结前的调整不产生新版本**——还在草拟阶段。一旦冻结，后续任何改动提升版本号，并在报告中注明本次评测依据的是哪个版本。

## 输出格式

`spec.json`：

```json
{
  "spec_version": "1.0",
  "frozen_at": "<ISO 8601 时间>",
  "workspace": "<被测工作区绝对路径>",
  "output_dir": "<运行目录绝对路径>",
  "upstream": {
    "profile": { "step": 2, "file": "rag-profile.json" },
    "query_plan": { "file": "query-plan.json" },
    "adapter_hash": "<接入层指纹>"
  },
  "corpus_snapshot": {
    "stores": [
      { "path": "vector_db", "collections": [ { "name": "<集合名>", "count": 0 } ] }
    ],
    "sample_file": "corpus-sample.jsonl",
    "sample_count": 0
  },
  "topics": { "weights": {}, "descriptions": {} },
  "query_styles": { "weights": {}, "descriptions": {} },
  "size": {
    "total": 0,
    "unanswerable": 0,
    "min_per_cell": 0,
    "cells": [ { "topic": "<方向>", "style": "<形态>", "n": 0 } ],
    "reportable": { "individual": [], "merged": [] }
  },
  "scoring": {
    "judge": { "executor": "<判定由谁执行>", "model": "<模型>", "rubric": "<分级口径>" },
    "hit_definition": "answer_points",
    "metrics": [
      { "name": "<指标>", "k": 0, "status": "available", "reason": null }
    ],
    "unanswerable_policy": "<无法回答样本怎么算>"
  },
  "generation": { "model": "<模型>", "temperature": null },
  "excluded": [],
  "user_provided_queries": [],
  "open_questions": []
}
```

字段说明：

| 字段 | 说明 |
|---|---|
| `upstream` | 上游产物与指纹。接入层指纹变化即表示本规格及其下游失效 |
| `corpus_snapshot` | 生成依据的语料快照。库变了，规格失效 |
| `size.min_per_cell` | 最小可报告样本量。**写出来**，不要藏在推导里 |
| `size.reportable` | 哪些方向/格子能单独出结论，哪些只能合并。第⑧步出报告时必须遵守 |
| `scoring.hit_definition` | 判定粒度。默认 `answer_points` |
| `scoring.metrics[].status` | `available` 或 `unavailable`；后者必须在 `reason` 写明原因 |
| `excluded` / `user_provided_queries` | 从第③步继承，供第⑤步生成时遵守 |
| `open_questions` | 仅阻塞性问题 |

**顶层字段集合固定，不要新增。**

## 完成后

向用户报告以下四项，然后停下：

1. 规格版本号与冻结时间
2. 规模与分格：总量、各方向各形态的条数、无法回答样本的配额
3. 可报告性：哪些方向能单独出结论、哪些只能合并
4. 判定口径与指标清单（含不可计算的项及原因）

结尾按 SKILL.md 的「每步的收尾」写。例如：

> 以上是规格 v1.0 的内容。请确认规模与分格、哪些结论能单独下、以及判定口径；如果确认无误，下一步是按这份规格生成评测集。需要推进吗？
