# 第⑤步：打样

## 目标

按**已冻结的规格**做几件样品，交用户确认，拿到"点头"之后才好开全量。

**这是产前打样，不是生成评测集。** 样品只回答一个问题：按这个样子做出来，行不行。

## 前置

- 运行目录中已有 `spec.json`，用户已确认冻结

## 本步不做的事

- **不生成全量评测集**（第⑥步）
- **不改规格。** 方向或形态本身有问题，回第④步提升版本号，不要就地改
- **不评价被测系统**，不对样品做检索验证（第⑦步）
- 不重新归纳方向（第③步）、不重算规模（第④步）

## 第一段：抽出题素材

**直接从向量库抽样，不要走接入层的检索入口。**

理由：用方向名去检索、拿返回的块出题，等于"用系统能检索到的内容去考系统"——循环论证，指标会虚高。抽出来的块系统可能根本检索不到，**那正是要被测出来的东西**。

沿用第②步探测脚本的思路（只读库、确定性抽样、不做随机）。

**配额**：按 `spec.topics.weights` 分配到各方向。

**数量**：按**全量出题数**准备，不是按样品数。需要的素材块数 **≥ 出题总数**——每块只出一道题，同一块反复出题等于重复样本、会虚高置信度。出 140 道题就至少要 140 个不同的块，实际取 150–200 个供筛选。

素材池是给第⑥步一起用的，本步只从里面挑几块做样品。

**落盘**为 `corpus-source.jsonl`，每行一个块：

```json
{ "id": "<块标识>", "text": "<块正文>", "topic": "<分配给哪个方向>", "chain": "<取自哪个集合>" }
```

## 第二段：打样

**先做几个样品给用户看，点头了再开全量。** 和工厂一样——流水线开动之前，先做几件样品确认样子对不对。

样品要回答的是"按这个做出来行不行"，所以**几个能代表成品的实例就够了**。这是打样，不是抽样调查：不需要讲究挑选规则，样品不完美也没有后果，用户看了不满意再调整就是。

方向和形态已经在上一步统计并落盘，**全量生产时每一个都会出题**。样品的作用只是让用户提前看一眼大方向。

### 样品数量

**每格一条**（方向 × 形态），**最多 20 条**。

- 格子数 ≤ 20 → 全覆盖，反正不多
- 格子数 > 20 → 取方向权重最高的 20 个，每个方向一条，形态在期间轮换

**怎么取自己定，不要为此问用户。**

形态数由 `spec.query_styles.weights` 决定，**不要假设只有两种**，也不要把形态数写死在规则里。权重为 0 的形态不出题，也不需要在样品里出现。

### 样品不是生产清单

**没被做成样品的格子，全量生产时照样出题。** 这一点必须写清楚，否则很容易顺手把没打样的内容省掉：

- 规格里**每一个格子**都要出题
- 权重低的方向（比如占比 3% 的边缘方向）不做样品，**但全量生成时必须按它的权重出题**
- **无法回答的样本**有独立配额，一条都不能少

**样品只是几个给人看的实例**——既不是生产清单，也不是"覆盖了才生产"的验收标准。它的条数与 `spec.size` 无关。

### 每条样品要包含

- 题目正文
- 它属于哪个方向、哪种形态
- **答案要点**——必须露出来。用户最容易发现的问题就是"答案抓错了"，只给题目看不出来
- **`note`（可选）**：用户口头交代的、不方便体现在规格里的写法提示

**要点必须来自真实块**，不能凭空写。源块取自第一段抽出的素材。

### note 用来说明"怎么写"，不用来说明"写什么"

交样过程中用户常会补一句"我们问职业的时候一般会带上职业名""这个方向的问法更口语"——这些是**对生成的指导**，记在样品的 `note` 里。

**判据是它改不改生成的内容：**

| 会改变生成什么 | 只是让写法更像 |
|---|---|
| 进规格（改格子配额，或写进 `generation.constraints`） | 记在样品的 `note` 里 |
| 例：问职业时一般用关键词 → 改 `size.cells` | 例：问职业时用户一般会带上职业名 |

**`note` 是提示，不是契约。** 它跟着样品一起交给生成者，作为范例的一部分；**不参与校验，也不进报告**。别把它当成规格的一部分去核对。

同方向或同形态的共性提示，写在多条样品上可以，但**更省事的做法是直接进规格的 `generation.constraints`**——那样它能被生成与校验一起引用。

### 呈现形式

按方向分组，形态用括注标在行内。

```
<方向一>（14.3%）
  · <题目>                                      〔自然语言问句〕
      要点：<答案要点>
  · <题目>                                      〔口语化简问〕
      要点：<答案要点>

<方向二>（14.3%）
  ...
```

### 顺便做泄漏检查

拿这几件样品算 **query 与源块的字符 n-gram 重合度**。

重合度过高说明生成时在照抄原文——那样这条题目等于把答案喂进去，检索难度被人为降低。**在打样时发现，比全量生产几百条之后再发现便宜得多。**

做法：算出每题的重合度，报告分布，并点名最高的几条让用户看。**不要自动下结论**，数字给人看。

## 第三段：交样

把样品交给用户，**明确请他看两件事**：

- 题目像不像线上真会问的
- 答案要点抓对没有

**同时说明哪些组合这次没有打样，并问他要不要再看别的**：

> 这次没给你看的组合还有：<方向 A × 形态 X>、<方向 B>……
> 它们照样会生产。如果你想知道某个方向、某种问法，或者换个规模大概会怎么出题，告诉我就补上。

用户说"可以"才进入第⑥步。指出具体条目有问题，就地改；**点名要看别的方向或形态，就再打几件样品给他看**。

**两种问题要分清：**

| 问题 | 处理 |
|---|---|
| 某几条题目写得不好、要点抓错 | 就地改，改完的版本进最终集 |
| 方向或形态本身不对 | **回第④步**提升规格版本号，不在本步改 |

### 样品什么时候落盘

**迭代过程中不落盘**——样品会反复改，每改一次写一个文件既没用，也和"产物不覆盖"打架。改到用户点头为止，都在对话里。

**用户说"可以"之后，写一份 `samples.jsonl`**：

```json
{ "id": "s001", "topic": "<方向>", "style": "<形态>",
  "question": "<题目>", "expected_points": ["<要点>"],
  "source_chunk_id": "<源块>", "note": "<写法提示，可空>" }
```

这份确认稿有三个用处：

- 第⑥步分片生成时的 few-shot 范例来源
- 最终 `eval-set.jsonl` 里 `pilot: true` 那些条目的来源
- **`note` 的载体**——生成时跟着范例一起给到生成者

样品本身很便宜——源块都在 `corpus-source.jsonl` 里，真丢了重新出题也用不了多久。

### 用户改过的样品是资产

确认过的样品**就是全量生产时的 few-shot 范例**。分片生成最容易出的问题就是各片风格不一致，同一个范例块给到每一片能压住这个偏差。

## 输出格式

`corpus-source.jsonl`（第一段）与 `samples.jsonl`（第三段），格式见上。

**顶层字段集合固定，不要新增。**

## 完成后

向用户报告以下四项，然后停下：

1. 样品清单：方向、形态、题目与答案要点
2. 哪些组合这次没有打样
3. 泄漏检查结果（n-gram 重合度分布，点名最高的几条）
4. 产物位置：`samples.jsonl` 与 `corpus-source.jsonl`

结尾按 SKILL.md 的「每步的收尾」写。例如：

> 以上是几件样品。请看一下题目像不像线上会问的、答案要点有没有抓错；如果确认无误，下一步就按规格开全量——预计 N 条，把每个方向每个形态都按比例覆盖到。需要推进吗？
