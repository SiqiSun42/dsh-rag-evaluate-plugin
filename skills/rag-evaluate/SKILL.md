# RAG 系统评测

评测工作区中已有的 RAG 检索系统。全程分为九个步骤，每步产出落盘产物，供后续步骤读取。

分步做法不在本文件里。加载本 skill 时会一并给出资源目录的位置，各步的具体做法位于其下的 `references/`，按需读取。

## 全局规则

以下规则适用于全部步骤：

1. **只写入输出目录。** 不改动被测工作区里的任何已有文件；不在输出目录之外创建任何文件或目录。
2. **进度由产物决定，不依赖记忆。** 每次开始工作前先执行下方"开始之前"并检查产物，不要假设，不要凭印象。
3. **每步完成即停。** 完成当前步骤后向用户报告并停下，不自行推进。收尾的话按下方「每步的收尾」写。
4. **产物不覆盖。** 目录或文件同名冲突时追加后缀，保留既有产物。
5. **区分实测与推断。** 推断得出的字段必须标注来源，不得与实测值并列而不加区分。**用一个可测量的量去代理一个测不到的机制时**（例如用长度代理"被硬切"），要么先抽几条实际内容确认这个代理成立，要么全程写明它只是代理——不要给它起一个像机制的名字，然后当机制用。
6. **未知与已知不同。** 表示能力的字段用 `true` / `false` / `null` 三态，`null` 表示未能确定，不要用 `false` 冒充未知。
7. **未实现的步骤不要执行。** 不要用想象的做法替代尚未定义的过程；缺什么就如实说明。
8. **发现异常只记录，不调查。** 任何一步发现可疑现象——结果不相关、指标偏低、内容对不上、返回值奇怪——就记录事实、提示用户，然后停下。**原因分析属于第⑨步。** 在本步展开调查会消耗大量资源，而且往往缺乏后续步骤才有的证据。
9. **只做本步定义的事。** 每一步都有明确的边界，越界产生的结论没有依据。判断不了就留 `null` 或如实说明，不要代替后续步骤下结论。
10. **严格按当前系统测评。** 不改写查询、不调整参数、不改阈值、不补后处理。系统原有的机制一律保留，**不添加也不删除**——哪怕某个机制看起来是错的、多余的，那也是要被测出来的东西。改进建议属于第⑨步。
11. **完成判据是本步的输出格式。** 格式里定义的字段填满，本步就结束。**不要添加格式之外的字段**——想加字段，通常说明做了本步不该做的事。
12. **优化冲动要顶住。** 写得顺手时容易顺手"改好一点"。任何这类改动的后果都由用户承担，且会让测评不再代表他的系统。不确定该不该加，就问用户，不要自己决定。
13. **报告只写本步的结论。** 与本步职责无关的发现一律不写——包括测试工作区之外的探查结果、其他步骤该管的问题、顺带看到的有趣现象，哪怕它看起来有用。**读到什么不重要，写什么才重要。**
14. **事实以最新一次实测为准。** 后续步骤的深度检查如果发现前面写下的内容与现实不符，**直接覆盖**，不要为了前后一致而保留旧值——前面因为只做了浅层判断、或用了不同方法而写得不准的，一律让位于新的事实。`gaps` 这类按判据过滤的清单，每次写入时都要按当前判据**重新过一遍**。
    两条边界不能越：**覆盖必须有新的实测依据**，不能凭印象改；**不能编造**，没测到的东西就留 `null` 或如实说明。
15. **记录必须反映实际生效的东西。** 字段里写的规则、默认值、推导过程，只在用户没有改动它们时才成立。**一旦用户做出了不同的选择，该字段就要改写成实际生效的内容，不能留着默认值**——否则别人按记录复算，会得出和你不一样的结果。这条适用于所有产物里的所有字段，不只是比例。

## 每步的收尾

每步结束时，用一段**面向用户**的话收尾，包含三件事：

1. 请用户确认本步的产出——明确说要确认什么
2. 如果确认无误，下一步会做什么——一句话，用日常说法
3. 问是否需要推进

**面向用户的文字里不要出现内部说法**——"按 skill 规则""第 N 步到此为止""不继续执行第 N 步"这类都不行。安装插件的人不会去读 skill，他读的是结论和下一步。

**报告正文同样适用。** `要动`、`不要动`、`不做判断` 这些判定用语，以及"本插件""本步""按规格"，都是给 Agent 看的分类。用户读报告时不需要知道有这套分类——他要看的是「这层怎么样、要不要改」，用正常说话写出来。

正例：

> 请确认上面的内容主题归纳。如果确认无误，下一步是确认查询计划——评测集要模拟哪些问题方向、用什么问法提问，以及各自的比例。需要推进吗？

反例：

> 按 skill 规则，第②步到此为止，不继续执行第③步（确认查询计划）。

## 被测工作区与输出目录

**被测工作区**是被评测的 RAG 系统所在的那个目录，不一定是会话工作区：

- 会话工作区本身就是被评测系统时，两者相同
- 被评测系统位于会话工作区的某个子目录时，**被测工作区取该子目录**
- 会话工作区内存在多个互不相干的候选系统、无法判断时，向用户确认

单次运行的全部产物放在被测工作区下的同一目录：

```
<被测工作区>/evaluation/<运行标识>/
```

运行标识使用时间戳，例如 `20260915-204400`。同一运行的产物不要散落到别处。

目录内放置归属标记文件 `.rag-evaluate.json`，用于识别该目录是否由本插件创建。

## 开始之前：确定本次运行

每次开始工作都先执行这一段。

**1. 被测工作区下没有 `evaluation/`**

新建目录，写入归属标记，本次为首次运行。

**2. 已存在 `evaluation/`，但没有归属标记**

该目录可能不属于本插件（也可能是更早版本创建的）。**不要写入。** 向用户说明情况，并询问是改用其他目录名，还是确认该目录可用于本插件。

**3. 已存在 `evaluation/`，且有归属标记**

属于本插件的历史运行。先列出已有运行及其产物，再询问用户：

- **接着某一次继续**：读取该次已有产物，按下节判断进度，从下一步继续，不重复已完成的步骤
- **新建一次运行**：在 `evaluation/` 下建立新的运行目录，**不修改任何既有运行的产物**，两者并存

新建运行不继承既有运行的产物。

## 随时可以回退

**用户在任何一步都可以要求修改之前定下的东西，不必等当前步骤走完。** 不要因为"已经做到第 N 步了"就劝他别改——前面每一步都是他确认过的，他有充分的理由改主意。

**回到哪一步，看他要改什么：**

| 想改什么 | 回到 |
|---|---|
| 换或增加评测链路、换运行环境、换接入层 | 第②步 |
| 方向、形态、比例 | 第③步 |
| 规模、判定标准、生成设定、格子配额 | 第④步 |
| 样品本身 | 第⑤步 |
| 某几道题目 | 第⑥步 |

**回退后要把受影响的下游重走一遍**，不要只改一处就往下走：

- 第②③步变了 → 第④步的规格要重新冻结（版本号 +1）
- 第④步的规格变了 → 样品与评测集都失效，要重打样、重生成
- 第⑤步的样品变了 → 第⑥步的评测集要重新生成
- 第⑥步的评测集变了 → 第⑦步及之后失效

**同一次运行内重做，原地更新同名产物**——那是同一份东西的新版本，不是一份新产物。规格用它自己的 `spec_version` 记录版本，报告注明依据的是哪一版。

**用户想保留两版做对比时，让他新建一次运行。** 不要在同一次运行里并存两个版本，那样"报告依据哪一版"就说不清了。

## 流程与产物

进度依据运行目录中已存在的产物判断：

| 步骤 | 内容 | 主要产物 | 分步说明 |
|---|---|---|---|
| ① | 清点：确认向量库与查询入口是否存在，整理候选链路 | `rag-profile.json` | `references/step-01-inventory.md` |
| ② | 探测画像：确认运行环境；向量库的规模、维度、内容主题与质量缺陷；入口的烟测与返回值形态 | 扩展 `rag-profile.json`，产出接入层（`adapter-spec.json` 或代码适配器）与 `corpus-sample.jsonl` | `references/step-02-profile.md` |
| ③ | 确认查询计划：方向与形态及其比例 | `query-plan.json` | `references/step-03-query-plan.md` |
| ④ | 冻结规格：把已确认的查询计划连同规模、判定标准固化为带版本的规格 | `spec.json` / `spec.md` | `references/step-04-freeze-spec.md` |
| ⑤ | 打样：抽素材，做几件样品交用户确认 | `corpus-source.jsonl`、`samples.jsonl` | `references/step-05-prototype.md` |
| ⑥ | 全量生成：按规格覆盖全部方向与形态，校验后落盘 | `eval-set.jsonl` | `references/step-06-generate-set.md` |
| ⑦ | 执行与判定：批量检索、分片判定、聚合指标 | `raw-results.jsonl`、`judgments.jsonl`、`metrics.json` | `references/step-07-run-and-judge.md` |
| ⑧ | 效度校验：确认本次运行结果可信，不通过时指明退回哪一步 | `validation.json` | `references/step-08-validate.md` |
| ⑨ | 归因分析：定位问题层级，给出建议 | `report.md` | `references/step-09-analyze.md` |

## 判断当前进度

1. 列出该运行目录中已有的产物。
2. 对照上表推断当前步骤：

   - 无产物 → 第①步未开始
   - `rag-profile.json` 中 `step` 为 1 → 第①步完成，下一步是第②步
   - `rag-profile.json` 中 `step` 为 2 → 第②步完成，下一步是第③步
   - 存在 `query-plan.json` → 第③步完成，下一步是第④步
   - 存在 `spec.json` → 第④步完成，下一步是第⑤步
   - 存在 `samples.jsonl` → 第⑤步完成，下一步是第⑥步
   - 存在 `eval-set.jsonl` → 第⑥步完成，下一步是第⑦步
   - 存在 `metrics.json` → 第⑦步完成，下一步是第⑧步
   - 存在 `validation.json` → 第⑧步完成，下一步是第⑨步
   - 存在 `report.md` → 第⑨步完成，本次运行结束

3. 向用户说明判断结果后再继续。
